# Spec: ระบบบริหารจัดการแคดดี้ (Caddy Management System)

## Problem Statement

รีสอร์ทกอล์ฟบริหารจัดการแคดดี้ด้วยกระบวนการที่ไม่มีระบบดิจิทัลรองรับ ทำให้เกิดปัญหา 3 ด้านพร้อมกัน:

1. **การจัดคิวออกรอบไม่มีมาตรฐานที่ตรวจสอบได้** — ไม่มีบันทึกว่าใครมาก่อน-หลัง ใครออกรอบไปแล้วกี่ครั้ง ทำให้ตรวจสอบความเป็นธรรมของคิวย้อนหลังไม่ได้
2. **ไม่มีทะเบียนประวัติ/สถานะแคดดี้ที่รวมศูนย์** — ไม่รู้ภาพรวมว่าวันนี้มีแคดดี้กี่คนพร้อมทำงาน ใครแจ้งลาไว้ล่วงหน้า
3. **การคำนวณและปิดยอดค่าจ้างทำด้วยมือ** — เสี่ยงต่อความผิดพลาดในการคำนวณตามจำนวนหลุม และไม่มีขั้นตอนปิดยอด/อนุมัติจ่ายที่เป็นระบบก่อนโอนเงินผ่านธนาคาร

## Solution

เว็บแอปพลิเคชันภายในองค์กร (on-premise, PHP + MySQL/MariaDB) เป็นระบบหลัก ที่ให้:

- พนักงานคุมคิว (รวมบทบาท HR) บันทึกแคดดี้เข้าคิวแบบ FIFO, ปรับสถานะแคดดี้ (พร้อม/ออกรอบอยู่/รอ/ลา), จัดการทะเบียนประวัติแคดดี้ (รวมดูสรุปรายการส่วนตัวของแคดดี้แต่ละคน), บันทึกการลา, และรับจองแคดดี้ล่วงหน้าแทนลูกค้า
- ฝ่ายบัญชีปิดยอดค่าจ้างเป็นรอบรายสัปดาห์ และ export รายการเป็น CSV/Excel เพื่อโอนเงินผ่าน SCB
- ผู้ดูแลระบบจัดการบัญชีผู้ใช้งานและสิทธิ์

ระบบทำงานเป็นอิสระ ไม่เชื่อมต่อกับระบบจองสนาม/tee time ที่มีอยู่ และ**ไม่เปิดให้ลูกค้าเข้าถึงระบบเองโดยตรง** — พนักงานคีย์ข้อมูลรอบ/ลูกค้า/การจองล่วงหน้าเข้าระบบนี้โดยตรงเมื่อมอบหมายหรือรับจองแคดดี้

**ช่องทางเสริม:** แอป Android (native, แจกจ่ายเป็น APK ติดตั้งตรง ไม่ผ่าน Play Store) สำหรับบทบาทพนักงานคุมคิว/HR เท่านั้น ให้เข้าถึงข้อมูลคิว/ทะเบียน/การลาชุดเดียวกันกับหน้าเว็บผ่าน REST API — เป็นช่องทางเพิ่มสำหรับใช้งานเดินถือหน้าสนาม **ไม่ได้แทนที่หน้าเว็บ** หน้าเว็บของบทบาทนี้ยังคงใช้งานได้ครบเหมือนเดิมเสมอ ฝ่ายบัญชีและผู้ดูแลระบบใช้งานผ่านเว็บเท่านั้น ไม่มีแอปมือถือ

## User Stories

### คิวและสถานะแคดดี้

1. As พนักงานคุมคิว, I want ลงชื่อแคดดี้เข้าคิวตอนเริ่มวัน, so that ระบบรู้ว่าใครพร้อมทำงานและเรียงคิวตามลำดับที่มาถึง
2. As พนักงานคุมคิว, I want เห็นหน้าจอคิวแบบ real-time เรียงตามลำดับ FIFO, so that รู้ว่าคนต่อไปที่ควรได้ออกรอบคือใคร
3. As พนักงานคุมคิว, I want มอบหมายแคดดี้คนถัดไปในคิวให้ออกรอบกับลูกค้า พร้อมระบุจำนวนหลุม (9/18), so that ระบบบันทึกงานและคำนวณค่าจ้างได้ถูกต้อง
4. As พนักงานคุมคิว, I want บันทึกว่าลูกค้าต้องการแคดดี้คนใดคนหนึ่งเป็นการเฉพาะ (caddy request), so that มีข้อมูลอ้างอิงเวลาตัดสินใจว่าจะรอแคดดี้คนนั้นหรือเลือกคนอื่นแทน
5. As พนักงานคุมคิว, I want เห็นข้อความแจ้งเตือนเมื่อแคดดี้ที่ถูกขอชื่อไม่ว่าง, so that ตัดสินใจหน้างานได้เอง (ระบบไม่บังคับ logic ใดๆ)
6. As แคดดี้ (ผ่านพนักงาน), I want ให้พนักงานกดยืนยัน "พร้อมออกรอบอีกครั้ง" หลังจบรอบก่อนหน้า, so that ไม่ถูกดันเข้าคิวโดยที่ยังไม่พร้อม
7. As พนักงานคุมคิว, I want ปรับสถานะแคดดี้เป็นว่าง/ออกรอบอยู่/รอ/ลา ได้จากหน้าจอเดียว, so that ควบคุมคิวทั้งหมดจากจุดเดียว
8. As พนักงานคุมคิว, I want ให้แคดดี้ที่แจ้งลาล่วงหน้าไว้สำหรับวันนี้ถูกตัดออกจากคิวโดยอัตโนมัติ, so that ไม่เผลอเรียกคนที่ไม่ได้มาทำงาน
9. As พนักงานคุมคิว, I want บันทึกแคดดี้กลับเข้าคิวเองได้ถ้าคนที่แจ้งลาไว้เปลี่ยนใจมาทำงาน, so that ระบบไม่ปิดกั้นการทำงานจริงที่ยืดหยุ่นกว่าที่วางแผนไว้

### การจองล่วงหน้า

24. As พนักงานคุมคิว, I want บันทึกการจองแคดดี้ล่วงหน้าให้ลูกค้าที่โทร/แจ้งล่วงหน้า (ระบุวันที่, เวลา, ชื่อลูกค้า, จำนวนหลุม, และแคดดี้ที่ต้องการถ้ามี), so that รองรับลูกค้าที่ต้องการจองก่อนวันจริงได้ โดยไม่ต้องเปิดระบบให้ลูกค้าเข้าถึงเอง
25. As ระบบ, I want ดึงแคดดี้ที่มีการจองล่วงหน้าไว้ออกจากคิว FIFO ปกติโดยอัตโนมัติก่อนถึงเวลาที่จองไว้ (ค่าตั้งต้น 30 นาทีก่อนเวลานัด, ปรับได้), so that ป้องกันแคดดี้คนนั้นถูกส่งออกรอบอื่นไปก่อนถึงเวลานัดของลูกค้าที่จองไว้
26. As พนักงานคุมคิว, I want เห็นป้ายกำกับในคิวว่าแคดดี้คนไหนมีการจองล่วงหน้ารออยู่และเวลาใด, so that วางแผนมอบหมายงานอื่นในช่วงเวลาที่เหลือได้

### ทะเบียนประวัติและการลา

10. As พนักงานคุมคิว (บทบาท HR), I want เพิ่ม/แก้ไขข้อมูลประวัติแคดดี้ (ชื่อ, เบอร์โทร, เลขบัตรประชาชน, เลขบัญชีธนาคาร SCB, วันที่เริ่มงาน, สถานะใช้งาน), so that มีทะเบียนกลางของแคดดี้ทั้งหมด
11. As พนักงานคุมคิว (บทบาท HR), I want บันทึกคำขอลาของแคดดี้ล่วงหน้าพร้อมระบุประเภท (ป่วย/กิจ/พักผ่อน/อื่นๆ), so that วางแผนกำลังคนล่วงหน้าได้
12. As พนักงานคุมคิว (บทบาท HR), I want เห็นสรุปสถิติการลาแยกตามประเภทต่อเดือน, so that วิเคราะห์แนวโน้มการขาดงานได้
13. As พนักงานคุมคิว (บทบาท HR), I want เห็นรายชื่อแคดดี้ที่แจ้งลาไว้ล่วงหน้าสำหรับวันที่กำลังจะถึง, so that เตรียมกำลังคนสำรองได้ทัน
14. As ผู้ดูแลระบบ, I want ปิดใช้งานบัญชีแคดดี้ที่ลาออก/พ้นสภาพ โดยไม่ลบประวัติเก่า, so that ข้อมูลค่าจ้างย้อนหลังยังถูกต้องครบถ้วน
14a. As พนักงานคุมคิว (บทบาท HR), I want เปิดดูสรุปรายการส่วนตัวของแคดดี้คนหนึ่ง (จำนวนรอบที่ออก, ยอดค่าจ้างสะสม, ประวัติการลา) เพื่อแสดง/พิมพ์ให้แคดดี้ดูเมื่อแคดดี้มาขอดูด้วยตัวเอง, so that แคดดี้ตรวจสอบข้อมูลของตัวเองได้โดยไม่ต้องมีบัญชีล็อกอินของตัวเอง

### ค่าจ้างและการปิดยอดจ่ายเงิน

15. As ผู้ดูแลระบบ, I want ตั้งค่าอัตราค่าจ้างแยกตามจำนวนหลุม (9 หลุม / 18 หลุม), so that ระบบคำนวณค่าจ้างของทุกรอบที่มอบหมายได้อัตโนมัติและถูกต้อง
16. As ฝ่ายบัญชี, I want เห็นสรุปยอดค่าจ้างที่ต้องจ่ายแต่ละแคดดี้สำหรับรอบสัปดาห์ปัจจุบัน (รวมจากทุกรอบที่ออกในสัปดาห์นั้น), so that ตรวจสอบความถูกต้องก่อนปิดยอด
17. As ฝ่ายบัญชี, I want กด "ปิดยอด" สำหรับรอบสัปดาห์หนึ่งๆ เพื่อล็อกยอดไม่ให้แก้ไขย้อนหลังโดยไม่ตั้งใจ, so that ยอดที่โอนเงินจริงตรงกับยอดในระบบเสมอ
18. As ฝ่ายบัญชี, I want export รายการยอดจ่ายของรอบที่ปิดแล้วเป็นไฟล์ CSV/Excel, so that นำไปคีย์โอนเงินผ่านระบบธนาคาร SCB ที่ใช้อยู่ได้
19. As ฝ่ายบัญชี, I want ดูประวัติยอดจ่ายของรอบสัปดาห์ก่อนหน้าทั้งหมด, so that ตรวจสอบย้อนหลังหรือรองรับการตรวจสอบบัญชีได้

### แอป Android (ช่องทางเสริมสำหรับพนักงานคุมคิว/HR)

27. As พนักงานคุมคิว, I want ล็อกอินและเห็นคิว/ปรับสถานะแคดดี้ผ่านแอป Android บนแท็บเล็ต/มือถือที่เดินถือได้, so that ไม่ต้องวิ่งกลับไปที่คอมพิวเตอร์ห้องแคดดี้ทุกครั้งที่ต้องอัปเดตสถานะ
28. As พนักงานคุมคิว, I want ให้ข้อมูลที่แก้ผ่านแอปกับหน้าเว็บซิงก์กันทันที (ข้อมูลชุดเดียวกัน), so that ไม่เกิดความสับสนว่าข้อมูลไหนล่าสุดกว่ากัน
29. As ผู้ดูแลระบบ, I want ให้แอปใช้ได้เฉพาะบัญชีที่มีบทบาทพนักงานคุมคิว/HR เท่านั้น, so that ฝ่ายบัญชีและแอดมินไม่ต้องพึ่งแอปนี้และไม่มีความเสี่ยงด้านสิทธิ์การเข้าถึงข้อมูลการเงิน

### สิทธิ์ผู้ใช้งานและระบบ

20. As ผู้ดูแลระบบ, I want สร้าง/แก้ไขบัญชีผู้ใช้งานและกำหนดสิทธิ์ (พนักงานคุมคิว/HR, ฝ่ายบัญชี, ผู้ดูแลระบบ), so that ควบคุมการเข้าถึงข้อมูลตามหน้าที่ความรับผิดชอบ
21. As ฝ่ายบัญชี, I want ไม่สามารถเข้าถึงหรือแก้ไขคิว/สถานะแคดดี้ได้, so that แยกความรับผิดชอบระหว่างงานปฏิบัติการกับงานการเงินชัดเจน
22. As พนักงานคุมคิว (บทบาท HR), I want ไม่สามารถเข้าถึงหน้าปิดยอด/export ไฟล์จ่ายเงินได้, so that ข้อมูลการเงินถูกจำกัดเฉพาะฝ่ายบัญชีเท่านั้น
23. As ผู้ใช้งานทุกคน, I want ล็อกอินด้วยอีเมล/รหัสผ่านของตัวเอง, so that มีการยืนยันตัวตนก่อนเข้าใช้งานระบบ

## Implementation Decisions

- **สถาปัตยกรรม:** PHP (ไม่ใช้ framework) + MySQL/MariaDB, รูปแบบเดียวกับระบบ `it-requisition` ที่มีอยู่แล้ว (PDO, session-based auth, role-based access ผ่าน `requireRole()`)
- **โมเดลข้อมูลหลัก:**
  - `caddies` — ทะเบียนประวัติแคดดี้ (ชื่อ, เบอร์โทร, เลขบัตรประชาชน, ธนาคาร/เลขบัญชี SCB, วันที่เริ่มงาน, สถานะใช้งาน)
  - `caddy_queue_status` — สถานะปัจจุบันของแคดดี้แต่ละคน (ว่าง/ออกรอบอยู่/รอยืนยันพร้อม/ลา) พร้อมเวลาที่เข้าคิวล่าสุด (ใช้เรียง FIFO)
  - `rounds` (หรือ `assignments`) — บันทึกการมอบหมายแคดดี้ออกรอบแต่ละครั้ง: แคดดี้, จำนวนหลุม (9/18), ชื่อลูกค้า (คีย์อิสระ ไม่ผูกระบบจองภายนอก), เวลาที่เริ่ม/จบรอบ, ธงระบุว่าลูกค้าขอชื่อแคดดี้นี้หรือไม่, ค่าจ้างที่คำนวณได้, สถานะ (`scheduled` สำหรับจองล่วงหน้า / `in_progress` / `completed`), วันเวลาที่นัดไว้ (สำหรับ `scheduled`)
  - `leave_requests` — คำขอลา (แคดดี้, ประเภทลา, ช่วงวันที่, หมายเหตุ) ไม่มีฟิลด์โควตา
  - `leave_types` — ประเภทลาที่กำหนดได้ (ป่วย/กิจ/พักผ่อน/อื่นๆ)
  - `wage_rates` — อัตราค่าจ้างต่อจำนวนหลุม (แก้ไขได้โดยผู้ดูแลระบบ)
  - `payroll_periods` — รอบการปิดยอดรายสัปดาห์ (วันที่เริ่ม-สิ้นสุด, สถานะเปิด/ปิดยอด, วันที่ปิดยอด, ผู้ปิดยอด)
  - `payroll_items` — ยอดค่าจ้างต่อแคดดี้ต่อรอบ (สรุปจาก `rounds` ในช่วงวันที่ของรอบนั้น) — สร้างตอนปิดยอด และห้ามแก้ไขหลังปิดยอดแล้ว
  - `users` — บัญชีผู้ใช้งานระบบ พร้อม role: `queue_hr`, `accounting`, `admin`
- **Queue logic:** FIFO ตามเวลาที่แคดดี้เข้าสถานะ "พร้อม" ล่าสุด (คิวใหม่ทุกครั้งที่กลับเข้าสถานะพร้อม ไม่ใช่ตามลำดับเข้างานตอนเช้าเพียงอย่างเดียว) ระบบไม่มี logic อัตโนมัติสำหรับกรณี caddy request ชนกับคิว — เป็นการตัดสินใจของพนักงานหน้างานเสมอ
- **การจองล่วงหน้า (advance booking):** แคดดี้ที่มี `rounds` สถานะ `scheduled` ในอีกไม่เกิน 30 นาที (ค่าตั้งต้น ปรับได้) จะถูก**ตัดออกจากรายการที่หยิบเข้าคิว FIFO ได้โดยอัตโนมัติ** (ระบบคำนวณจากเวลาปัจจุบันเทียบกับเวลานัดตอน query คิว ไม่ต้องมี background job/cron) — ต่างจากกรณี caddy request ที่ไม่มี logic บังคับ เพราะการจองล่วงหน้ามีเวลานัดที่ชัดเจนกว่า จึงป้องกันอัตโนมัติได้โดยไม่เสี่ยง over-engineer
- **แอป Android เป็นช่องทางเสริม ไม่ใช่ระบบแยก:** แอปเรียกใช้ REST API ชุดใหม่ (endpoint สำหรับ login ด้วย token, ดูคิว, ปรับสถานะ, จัดการทะเบียน, บันทึกการลา) ที่อ่าน/เขียนตารางเดียวกันกับหน้าเว็บ PHP ทุกตาราง — ไม่มีฐานข้อมูลหรือ business logic แยกชุด หน้าเว็บของบทบาทพนักงานคุมคิว/HR ยังคงมีอยู่ครบและใช้งานได้อิสระจากแอป
- **แพลตฟอร์มแอป:** Android เท่านั้น แจกจ่ายเป็นไฟล์ APK ติดตั้งตรง ไม่ผ่าน Google Play ไม่รองรับ iOS
- **Payroll:** ปิดยอดเป็นรายสัปดาห์ (เลือกได้ว่าจะ fix เป็นวันจันทร์–อาทิตย์) คำนวณจากผลรวม `wage_rates` ตามจำนวนหลุมของทุก `rounds` ที่อยู่ในช่วงวันที่ของรอบ เมื่อปิดยอดแล้ว ข้อมูล `rounds` ที่เกี่ยวข้องถือเป็น read-only
- **Export ไฟล์ธนาคาร:** เวอร์ชันแรกส่งออกเป็น CSV/Excel ทั่วไป (ชื่อแคดดี้, เลขบัญชี, ยอดโอน) ให้ฝ่ายบัญชีคีย์เข้าระบบ SCB Business Banking เอง — เว้นจุดขยาย (เช่น interface/ฟังก์ชัน export แยกต่างหาก) ไว้สำหรับเสียบฟอร์แมตไฟล์ bulk transfer เฉพาะของ SCB เมื่อได้สเปกไฟล์จริงจากธนาคารในเฟสถัดไป
- **ทิป:** ไม่มีฟิลด์หรือตารางใดๆ เกี่ยวกับทิปในระบบ
- **สนาม:** ออกแบบสำหรับสนามเดียว/พูลแคดดี้เดียว ไม่มีแนวคิด "สนาม" ในโมเดลข้อมูล

## Testing Decisions

- ทดสอบพฤติกรรมภายนอก (external behavior) ไม่ทดสอบรายละเอียดการ implement — เช่น "หลังมอบหมายแคดดี้ออกรอบ คิวต้องไม่แสดงชื่อนั้นอีกจนกว่าจะกดพร้อม" ไม่ใช่ "ฟังก์ชัน X ถูกเรียกด้วยพารามิเตอร์ Y"
- โมดูลที่ต้องทดสอบละเอียดที่สุด (ความเสี่ยงสูงถ้าผิด):
  1. การคำนวณค่าจ้างต่อรอบและยอดรวมต่อรอบสัปดาห์ (กระทบเงินจริง)
  2. ลอจิกคิว FIFO และการตัดแคดดี้ที่ลาออกจากคิวอัตโนมัติ
  3. การล็อกข้อมูล `rounds`/`payroll_items` หลังปิดยอดแล้ว (ป้องกันแก้ไขย้อนหลัง)
  4. การจำกัดสิทธิ์ตาม role (ฝ่ายบัญชีเข้าคิวไม่ได้, HR เข้าปิดยอดไม่ได้)
- Prior art: ระบบ `it-requisition` ใช้รูปแบบทดสอบผ่าน curl end-to-end ยืนยันสถานะเปลี่ยนถูกต้องในฐานข้อมูลจริง (ไม่มี automated test suite) — แนะนำให้ตั้ง automated test (PHPUnit หรือเทียบเท่า) อย่างน้อยสำหรับข้อ 1 และ 3 เนื่องจากกระทบเงินโดยตรง ส่วนที่เหลือ smoke-test แบบ manual/curl ตามแพทเทิร์นเดิมได้
- **ข้อจำกัดด้านการทดสอบแอป Android:** เครื่องที่ใช้พัฒนาปัจจุบันไม่มี Android SDK/adb/Flutter ติดตั้งอยู่ (ตรวจสอบแล้ว) จึง **ไม่สามารถ build/รันแอปจริงเพื่อทดสอบ end-to-end แบบเดียวกับที่ทำกับระบบเว็บได้** ส่วนตั๋วของ REST API (backend) ยังทดสอบผ่าน curl ได้ตามปกติเหมือนระบบเว็บ แต่ส่วนแอปเองจะเป็นการเขียนโค้ด+เอกสารวิธี build/ทดสอบเองเป็นหลัก ความมั่นใจในผลลัพธ์จึงต่ำกว่าส่วนเว็บที่ยืนยันด้วยการรันจริงแล้ว หากต้องการทดสอบแอปจริง ต้องติดตั้ง Android Studio + SDK (หรือ Flutter SDK ถ้าเลือกใช้ Flutter) บนเครื่องที่จะ build ก่อน

## Out of Scope

- การเชื่อมต่อกับระบบจองสนาม/tee time ที่มีอยู่ (ตัดสินใจให้เป็นระบบอิสระ)
- **หน้าเว็บ/แอปสาธารณะให้ลูกค้าจองคิว/แคดดี้เอง** — พนักงานเป็นคนกดจองแทนลูกค้าเสมอ ระบบไม่เปิดสู่อินเทอร์เน็ต
- การบันทึก/แบ่งทิป
- โควตาการลาแบบมีผลผูกพันทางกฎหมายหรือสวัสดิการที่คำนวณอัตโนมัติ (แคดดี้เป็นอิสระ ไม่ใช่ลูกจ้างประจำ)
- การสร้างไฟล์ bulk transfer ตามฟอร์แมตเฉพาะของ SCB (รอสเปกไฟล์จากธนาคาร)
- การรองรับหลายสนามกอล์ฟ/หลายพูลแคดดี้
- การให้แคดดี้ล็อกอินปรับสถานะตัวเอง หรือดูข้อมูลของตัวเองเองโดยตรง (ทุกอย่างผ่านพนักงานคุมคิว/HR เท่านั้น)
- การไล่เกรด/ระดับแคดดี้ที่มีผลต่ออัตราค่าจ้าง
- **แอป iOS** — รองรับ Android เท่านั้น
- **การจ่ายเงินแบบครึ่งเดือน (15 วัน)** — พิจารณาแล้วแต่ยืนยันคงรอบรายสัปดาห์ตามเดิม

## Further Notes

- ก่อนเขียนโค้ดจริง ควรยืนยันชื่อฟิลด์/ประเภทข้อมูลของเลขบัญชีธนาคาร SCB (เลขบัญชี 10 หลักมาตรฐาน) กับฝ่ายบัญชีอีกครั้ง เผื่อมีข้อกำหนดพิเศษ
- เมื่อฝ่ายบัญชีได้สเปกไฟล์ bulk transfer ของ SCB มาในอนาคต ให้เพิ่มเป็นตั๋วใหม่แยกต่างหาก ไม่ต้องรื้อโครงสร้าง export CSV เดิม เพราะออกแบบให้เป็นจุดขยายไว้แล้ว
- **แอป Android เป็นงานเพิ่มความเสี่ยงสูงกว่าส่วนอื่นของระบบ:** ทีมที่มีอยู่มีประสบการณ์ตรงกับ PHP/MySQL (เห็นได้จากระบบอื่นในองค์กร) แต่ไม่มีหลักฐานว่ามีประสบการณ์พัฒนาแอป Android มาก่อน และเครื่องพัฒนาปัจจุบันยังไม่มีเครื่องมือที่จำเป็นเลย (Android SDK/Flutter/Android Studio) ควรวางแผนเวลา/ทรัพยากรสำหรับตั๋วนี้แยกจากส่วนเว็บ และพิจารณาว่าตั๋วแอปเป็นตั๋วที่ทำ**หลังสุด**และ**ทำได้ไม่สำเร็จก็ไม่กระทบระบบหลัก** เนื่องจากหน้าเว็บของบทบาทพนักงานคุมคิว/HR ใช้งานได้ครบอยู่แล้วโดยไม่ต้องพึ่งแอป
- เวลาที่ระบบตัดแคดดี้ที่มีจองล่วงหน้าออกจากคิว FIFO อัตโนมัติ (ค่าตั้งต้น 30 นาทีก่อนเวลานัด) เป็นค่าที่ประมาณไว้ตามความสมเหตุสมผล ควรยืนยัน/ปรับกับพนักงานคุมคิวจริงอีกครั้งตอน implement ตั๋ว 03
